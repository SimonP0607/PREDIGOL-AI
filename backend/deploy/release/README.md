# deploy/release - one way to build, ship and check a release

Plan CI/CD, phase C3. Until now every release was a folder of scripts generated by the session that made it (`/root/releases/<stamp>-<plan>/`),
copied from the one before. The scripts are now **versioned here**; a release is `build_kit.sh` + `gate.sh` + `ship.sh`.

```
gate.sh        CI of GitHub passed for the backend/ and web/ trees of the commit (any commit with the same trees counts)
build_kit.sh   makes refs/release/<part>-<name> (the next link of what production runs), the bundles, the scripts with the names filled in,
               RELEASE.json (commits, migrations, model-code fingerprint and guard verdict, the release's own checks), SHA256SUMS
ship.sh        copies the kit to the server, checks the hashes THERE, prints the command that starts the chain
               (--start --owner-ok starts it: the owner's word is what releases)
templates/server/   the scripts that run on the server (precheck, backup + restore test, deploy, smoke, verify, followups, chain.sh)
extras/             scripts of one plan that a release may add with --extras DIR (a file of the same name replaces the template's)
```

```
backend/deploy/release/gate.sh --head <commit>
backend/deploy/release/build_kit.sh --rel f11 --head <commit> --from-server predigol --parts backend,web --spec release_f11.json
backend/deploy/release/ship.sh --host predigol --kit ../releases/<stamp>-f11
# with the owner's word:
backend/deploy/release/ship.sh --host predigol --kit ../releases/<stamp>-f11 --start --owner-ok
```

`--from-server` reads the commits production runs (`/opt/predigol/{backend,web}`), fetches them if this clone lacks them and builds on top of
them; nothing is written on the server. `--spec` is a JSON merged into RELEASE.json: `precheck.objects_absent/columns_absent/tables_measured`,
`verify_checks[{name, sql, expect}]`, `verify_env[{container, name, expect}]` - the checks that are particular to the release.

What the chain does (unchanged from the proven kits): hashes -> precheck (read-only, waits only for "someone else is working") -> backup +
restore test (a restore test newer than the backup, of THIS dump) -> deploy with `predigolctl` (lock, quiet check, model-code guard in `stop`
mode, day digest before/after) -> smoke -> verify -> post-deploy reads -> follow-ups at 10/30/60 minutes. It stops at the first failure and
never rolls back by itself. The sections of the checks that came from the IA release (the AI tables, the promotion ledger) stay in the
templates because the objects exist in production now; a release that does not want them replaces the file through `--extras`.

Not here: deciding to release. That is the owner's, in his words, in Spanish, before `--start --owner-ok`.
